## Durable Outbox Design
Every local operation intended for synchronization is stored in IndexedDB `outbox`:
```typescript
interface OutboxEntry {
  operationId: string;       // Stable canonical UUID preserved across all retries
  taskId: string;            // Associated task UUID
  originDeviceId: string;    // Anonymous local device UUID
  status: OutboxStatus;      // 'PENDING' | 'IN_FLIGHT' | 'ACKNOWLEDGED' | 'BLOCKED' | 'FAILED'
  attemptCount: number;      // Number of submission attempts
  lastAttemptAt?: string;    // ISO timestamp of last attempt
  nextRetryAt?: string;      // ISO timestamp for exponential backoff
  lastError?: string;        // Human-readable error description
  createdAt: string;         // ISO timestamp of creation
  acknowledgedAt?: string;   // ISO timestamp of durable server acceptance
  serverSequence?: number;   // Server-assigned sequence number
}
```
Invariants verified:
- Local task mutation and outbox record persist in the exact same database transaction.
- Stable operation IDs: never regenerated across retries.
- Outbox state survives page refreshes and browser restarts.

## IndexedDB Migration
Dexie database version 4 migration was added without resetting or deleting user data:
```typescript
this.version(4).stores({
  outbox: 'operationId, taskId, status, originDeviceId, createdAt, nextRetryAt, [status+nextRetryAt], [taskId+status]',
});
```
During database open, `backfillLegacyOutbox` inspects existing local operations and backfills missing outbox entries as `PENDING` (or `ACKNOWLEDGED` if already recorded in `lan_synced_operations`).

## Queue State Machine
- `PENDING`: Awaiting transmission; eligible when `nextRetryAt <= now`.
- `IN_FLIGHT`: Currently transmitted over Socket.IO awaiting durable acknowledgment.
- `ACKNOWLEDGED`: Server confirmed durable SQLite commit (`APPLIED` or `ALREADY_APPLIED`).
- `BLOCKED`: Parent dependency missing or concurrent conflict detected.
- `FAILED`: Permanent schema or protocol validation error.
- Interrupted `IN_FLIGHT` entries recover to `PENDING` automatically on restart via `resetAbandonedInFlight()`.

## Automatic Reconnection
- Exponential backoff: $T = \min(30000, 1000 \times 2^{\text{attempt}-1}) \pm 20\%$ jitter.
- Sequence: ~1s -> ~2s -> ~4s -> ~8s -> ~16s -> 30s.
- Clean listener teardown prevents duplicate listeners across repeated reconnections.
- Manual "Disconnect" stops automatic reconnect; "Connect" resets state and initiates reconnect.
- Re-registers device with persistent `deviceId` and protocol version upon every successful socket connect.

## Retry Strategy
- Transient network drops, socket timeouts, or server restarts mark operations for retry with exponential backoff and jitter.
- Blocked operations remain persisted without infinite CPU-intensive retry loops.
- Permanent validation errors (`INVALID`, `UNAUTHORIZED`, `DUPLICATE_MISMATCH`) transition to `FAILED` for user inspection.
- Users can click "Retry Blocked & Failed Operations" to re-queue them as `PENDING`.

## Causal Replay
- Enforces strict parent-first causal ordering: operations on the same task are sorted by `revision` ascending before submission.
- Independent operations belonging to different tasks are ordered by creation timestamp.
- If a parent operation fails or blocks, all dependent child operations are marked `BLOCKED`.

## Incoming Synchronization
- Bounded batches are requested using the persistent local cursor.
- Operations are validated with Zod and applied using Phase 5 pure causal engine semantics.
- Deduplication by operation ID prevents duplicate mutations.

## Cursor Recovery
- Cursor safety: Local cursor advances monotonically only after each contiguous operation has successfully committed to local IndexedDB.
- Server database reset / replacement detection: If the server sequence count is lower than the local cursor, the cursor is safely reset to 0 to ingest the new server state without skipping operations.

## Conflict Handling
- If two devices concurrently modify a task while disconnected, both branches are preserved using Phase 5 causal ancestry.
- Server records conflict audit record and rejects with `classification: 'CONFLICT'`.
- Client records conflict in `db.conflicts` and marks outbox entry as `BLOCKED`.
- User resolves the conflict in the UI using Keep Local or Accept Incoming, generating a canonical `TASK_RESOLVE` operation.
- The resolution operation enters the outbox atomically, replays over LAN, and both devices converge.

## QR/LAN Interoperability
- PaperBridge QR-imported tasks are stored with `TASK_IMPORT` audit records and do NOT enter the outbox, preventing accidental forwarding or replay loops.
- Operations imported via QR and later encountered over LAN share stable operation IDs and revisions, avoiding duplicate tasks or revision corruption.
