## Synchronization Domain Model

Pure Zod-validated TaskChanges, TaskUpdatePayload, TaskAckPayload, SHA-256 canonical task-state hashing, task-change application, and causal classification independent of React, Dexie, or transport.

## QR Protocol Extensions

Kept v1 TASK_CREATE unchanged. Added explicit v2 TASK_UPDATE and TASK_ACK envelopes, version-aware decoding, checksum verification, strict schemas, and the existing 2,048-byte payload limit.

## Revision and Causality Rules

Normal updates advance one revision from a matching base state hash. Operation IDs provide idempotence; parent operation IDs and shared state hashes establish ancestry even across legacy v1 imports. Missing ancestors are rejected pending manual earlier QR transfer; concurrent branches are not silently overwritten. Resolution operations reference both branches and may advance beyond one revision.

## Outgoing Updates

Each local edit, status transition, deletion, or resolution can be selected individually. The first exported update's canonical message bytes and ID persist in the outgoing table and are reused for retries. Multiple edits are presented in revision order. The Send screen defaults to a recent resolution operation when present.

## Incoming Updates

The Receive screen distinguishes all three supported QR message types, previews proposed changes, and requires confirmation. Valid update application atomically writes task, operation, and import ledger. Duplicate, stale, invalid, conflicting, and missing-parent outcomes are explicit.

## Acknowledgments

An applied incoming update can produce a return ACK QR. The original sender records it only if message ID, operation ID, task ID, and revision match a stored outgoing update. Duplicate ACKs are idempotent and never increment task revision.

## Conflict Detection

Concurrent edits create one persistent conflict per incoming operation; local task state remains unchanged. Incoming candidate state and hash are validated against a known base. Deletion versus modification is handled as conflict.

## Conflict Resolution

Task Details compares local and incoming versions. Keep Local and Accept Incoming create a new TASK_RESOLVE operation, record merged branch metadata, and atomically close the conflict. The full chosen mutable state is QR-exportable and recognized by the other branch, allowing convergence. Resolve Later leaves the conflict pending.

## IndexedDB Migrations

Dexie version 3 adds outgoing, acknowledgments, and conflicts tables and ancestry indexes on operations. Version 1/2 tasks, operations, settings, imports, IDs, and multilingual fields remain unchanged. A migration test opens a seeded version 2 database and verifies data retention.

## Multilingual Compatibility

Task-state hashes and QR updates use canonical instruction codes and preserve free text unchanged. Language selection remains device-local and is not transferred or overwritten.

# 5. DEFINE REVISION AND CAUSALITY SEMANTICS

Implement deterministic revision handling.

### Normal update

A task is at revision 3.

A valid update references revision 3 as its base and produces revision 4.

Apply it atomically.

### Duplicate update

The same operation is scanned twice.

Do not apply it twice.

Do not increment the revision again.

Return an already-applied result.

### Stale update

A QR references an older task state.

Do not blindly overwrite the current task.

Classify it as stale or conflicting based on actual ancestry.

### Concurrent update

Two devices independently modify the same base state.

Do not silently choose one.

Record a conflict requiring user resolution.

### Future or missing-parent update

An update depends on an operation that is not locally known.

Do not apply it blindly.

Return a clear missing-history or out-of-order result.

If supporting deferred processing, persist it safely and document the behavior.

### Deleted tasks

Respect existing soft-deletion semantics.

Do not resurrect a deleted task automatically.

Deletion versus modification must be treated as a conflict when concurrent.

### Local edits

Inspect how Phase 2 increments revisions.

Integrate causal metadata into local task edits, not just QR imports.

Ensure all local update paths use the same revision semantics.

If historical tasks lack ancestry metadata, introduce a safe migration or compatibility policy.

Do not fabricate historical parent operations.
